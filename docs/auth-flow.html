The core rule

An interactive page talks to the server over a WebSocket. A WebSocket message has no HTTP response, and only an HTTP response can set or clear a cookie. So every flow is split in two:

Interactive page (circuit)

Shows the form, validates input, checks the password, handles lockout, shows messages. No page reloads.

HTTP endpoint

Receives a normal form POST and writes or clears the auth cookie in its response. Then redirects.

over the WebSocket (circuit) real HTTP request C# method call on the server return value

Where HttpContext exists

HttpContext only exists while an HTTP request is being handled. An interactive page lives in three moments, and only two of them are HTTP requests.

Login

The password is checked over the circuit. The cookie is set by a separate HTTP POST that carries a one-time ticket, never the password.

  1. The user fills in the MudBlazor form and clicks Sign in.
  2. Login.razor calls AccountService.ValidateCredentialsAsync.
  3. The service looks the user up. Unknown users are checked against a dummy hash so they take as long as a wrong password. A wrong password adds 1 to the failure count; at 5 the account locks for 15 minutes.
  4. The store returns the user.
  5. The service returns Success. If the stored hash is old, it is upgraded here. The page clears the password from memory.
  6. The page asks LoginTicketStore for a ticket: 64 random hex characters, valid 60 seconds, usable once.
  7. The page renders a hidden form (ticket, antiforgery token, ReturnUrl) and auth.js submits it.
  8. The browser sends a normal POST to /account/complete-login. The endpoint first validates the antiforgery token.
  9. It redeems the ticket. A second use of the same ticket fails.
  10. It reloads the user (still active?) and builds the claims.
  11. SignInAsync writes the __Host-App.Auth cookie, and the response redirects to the ReturnUrl, but only if that is a page on this site.
  12. The full page load starts a new circuit that is signed in.

Logout

Sign-out is always a POST with an antiforgery token. Opening a URL never signs anyone out, so a link on another site can't log your users out.

Forgot and reset password

The raw token only exists in the e-mail. The database stores its SHA-256 hash, so a leaked table can't be used to reset passwords.

  1. The user enters a username or e-mail on /Account/Forgot-Password.
  2. The page calls RequestResetAsync.
  3. If the account exists and is active, a random token is made and its hash is saved with a 30-minute expiry. Any older token for that user is replaced.
  4. The link is built from Auth:PublicBaseUrl, never from the request's Host header, and e-mailed.
  5. The page shows "If an account matches…" to everyone and takes at least 1 second, so it can't be used to find accounts.
  6. The user opens /Account/Reset-Password?token=… from the e-mail. The page checks the token on load.
  7. The user enters the new password twice.
  8. The page calls ResetPasswordAsync.
  9. Password rules are checked, the token is consumed (only one submit can win), the new hash is saved and the security stamp changes. That signs the user out on every other device. Any lockout is cleared.
  10. The page reloads to the login page with "Your password has been changed".

Session checks while the user works

Three limits apply to every session: 30 minutes idle (the cookie slides), 12 hours absolute after sign-in, and user still valid (active, password not changed). Two paths enforce them, because an open interactive page makes no HTTP requests.

Setup checklist

  • Program.cs: add builder.Services.AddAppAuthentication(builder.Configuration, builder.Environment);, register your IAuthUserStore and IAuthEmailSender, and add app.MapAccountEndpoints(); before MapRazorComponents. Remove the old cookie and auth-state-provider registration.
  • appsettings.json: add the "Auth" section with at least PublicBaseUrl.
  • Database: add PasswordHash, SecurityStamp, FailedLoginCount, LockoutEndUtc to the user table and create PasswordResetTokens. SQL is in docs/AUTH.md.
  • IAuthUserStore: implement it against your database. IAuthEmailSender: implement it with your SMTP service.
  • MainLayout.razor: add <LogoutForm @ref="_logout" />, a Sign out menu item that calls _logout.SubmitAsync(), and <IdleTimeoutMonitor />.
  • App.razor: keep <Routes @rendermode="InteractiveServer" /> with prerendering on. The antiforgery token comes from the prerendered page.
  • Existing passwords: either ask everyone to reset, or verify the old hash format once in your store and re-save with the new hasher on the next login.
// Program.cs (order matters)
builder.Services.AddAppAuthentication(builder.Configuration, builder.Environment);
builder.Services.AddScoped<IAuthUserStore, SqlAuthUserStore>();   // yours
builder.Services.AddScoped<IAuthEmailSender, SmtpAuthEmailSender>(); // yours

app.UseStaticFiles();
app.UseAuthentication();
app.UseAuthorization();
